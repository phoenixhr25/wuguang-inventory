# 穿搭组合发现算法

本文记录物光如何处理衣物增加后的组合爆炸问题，以及对开源衣橱项目的比较。

## 其他项目如何处理组合爆炸

开源项目大致采用四类方案。它们解决的问题并不完全相同：有的控制计算规模，有的只减少用户看到的数量，有的通过要求用户手动保存穿搭来回避自动生成。

| 路线 | 代表项目 | 核心方法 | 局限 |
|---|---|---|---|
| 确定性剪枝＋批量评分 | Aether Wardrobe | 规则生成候选，按正式度、季节和颜色冲突提前删除；小模型批量评分，只保存高分组合 | 需要较完整的衣物属性和组合数据层 |
| 规则预筛＋AI 选择 | Hangar、Wardrowbe | 先按天气、场合等压缩库存，再让 AI 返回少量库存 ID | 不保证搜索完整，每次推荐通常需要模型调用 |
| 人工保存＋标签检索 | Wardrobe | 用户建立确认过的穿搭，按季节、温度和标签过滤 | 维护成本较高，不能自动发现大量新组合 |
| 逐位置贪心选择 | 一些轻量衣橱项目 | 依次选择当前得分最高的上装、下装、鞋履和外套 | 速度快，但局部最优不一定形成整体最优 |

### Aether Wardrobe：目前最完整的参考实现

Aether Wardrobe 把组合表作为推荐的事实来源：

```text
新增衣物
→ 确定性候选引擎生成结构合法的组合
→ 正式度、季节和明显颜色冲突剪枝
→ 每 12 套交给小模型批量评分
→ 只保存评分不低于 7 的组合
→ 每日根据场合、天气和近期穿着查询
→ 小模型只重排少量候选并解释
```

这种方法把大量计算放在新增衣物时，日常推荐只需查询已经通过筛选的组合。AI 不负责凭空创造组合，也不需要每天重新理解全部库存。

### Hangar 与 Wardrowbe：减少输入，而非完整枚举

这类方案先利用天气、场合、季节或最近穿着缩小衣物集合，再让模型直接给出一至数套建议。用户不会面对大量组合，但系统未必搜索了全部可行组合。它适合“今天直接告诉我穿什么”，不适合完整浏览组合空间。

### Wardrobe：通过人工确认回避爆炸

Wardrobe 主要检索用户已经建立并保存的穿搭。季节标签可以关联日期或温度范围，再结合多标签筛选。这种方式结果可靠，但需要用户提前维护组合，与物光降低录入成本的原则存在张力。物光可以借鉴标签结构，不应要求普通用户手动建立全部组合。

### 物光当前方案与技术边界

物光 V0.2 当前采用：

```text
有界笛卡尔积
→ 最多生成 2,000 个候选
→ 指定单品筛选
→ 按场合历史和穿着次数排序
→ 每次展示 6 套
```

这个方案解决了手机端的计算阻塞和展示过载，也不产生模型费用。其边界是：超过 2,000 套后，后续组合可能从未进入候选池，候选生成顺序可能造成偏差；场合目前用于记录和历史排序，还不能判断衣服是否真正适合该场合。

### 物光下一阶段算法

下一阶段应从“先生成 2,000 套再排序”升级为“边生成、边剪枝、边保留 Top-K”：

```text
生成一个结构合法的组合
→ 温度、降雨、场合和互斥规则硬过滤
→ 计算确定性基础分
→ 用最小堆持续保留得分最高的 50—100 套
→ AI 只复核前 20—50 套并生成解释
→ 最终向用户展示 3—6 套
```

初始评分可以采用：

```text
总分 =
场合适配 30%
+ 温度天气适配 25%
+ 颜色与风格协调 20%
+ 用户历史偏好 15%
+ 低使用率探索奖励 10%
```

权重必须通过真实采用数据调整，不应长期依赖主观设定。用户的“穿了、收藏、不适合、替换一件”是比模型文字评价更重要的反馈。

### 技术决策

物光采用混合路线：

1. 当前免费本地版继续使用有界候选池，保持零模型费用和快速响应；
2. 增加天气、正式度、季节和场合等结构化字段后，引入硬规则剪枝；
3. 使用 Top-K 队列避免候选顺序偏差和完整排序成本；
4. 只有经过规则筛选的少量候选才交给便宜模型评分；
5. 模型只能返回真实库存 ID，服务端验证后才能展示；
6. 长期保存用户穿过、收藏或否定的组合，临时候选无需全部入库。

## 物光应保留和改进的部分

### 保留

- 照片作为录入入口；
- AI 输出结构化 JSON；
- 低置信度时人工确认；
- 天气预筛，再交给模型搭配；
- 指定一件衣物，让系统围绕它搭配；
- 避免连续推荐最近穿过的衣物；
- 保存穿搭、穿着次数和用户反馈；
- 支持 OpenAI 兼容接口，避免被单一模型绑定。

### 改进

Hangar 的 AI 结果基本自动写入数据库。物光更适合采用“候选箱”：

```text
AI 已识别 → 用户看一眼 → 修改或确认 → 正式入库
```

这样可以避免品牌、材质、数量和价格误判直接污染个人物品库。

重复检测不应只比较文字字段。后续应加入图片向量相似度，再结合名称、颜色和类别判断。

搭配结果需要额外验证完整性，例如：

- 必须包含上装＋下装，或者连衣裙；
- 鞋履可以缺省，但要明确提示；
- 下雨时优先防水鞋和外套；
- 高温时排除厚重外套；
- 用户指定的衣物必须出现；
- 不能同时选择两件互斥的同类主件。

## 最小技术方案

当前物光把 HTML 放在 Streamlit iframe 中，物品数据存于浏览器 IndexedDB。API 密钥绝不能写进前端 JavaScript，否则任何访问者都能取走密钥。

AI 版本至少需要一个服务端接口：

```text
浏览器照片
   ↓
物光服务端 /api/analyze-item
   ↓
DeepSeek / Gemini / OpenAI / Ollama
   ↓
结构化候选结果
   ↓
浏览器人工确认后写入本地物品库
```

第一阶段仍可保留本地物品库，只把压缩后的单张照片临时发到服务端识别，处理完成后删除。这样暂时不需要用户账户和云数据库。

Streamlit Community Cloud 不适合直接承载自定义 FastAPI 路由。低成本验证有两条路径：

1. 用 Streamlit 原生控件做一页独立的“AI 识别实验室”，密钥放在 `st.secrets`；
2. 部署一个很薄的 FastAPI 服务，让现有前端调用，后续可平滑接账号、额度和支付。

推荐先走第 1 条验证识别质量；确定有人持续使用后，再走第 2 条形成正式产品。

## 模型选择

### DeepSeek

当前 `deepseek-flash` 已支持图片输入、JSON 输出和 OpenAI 兼容接口，适合低成本视觉识别与文本穿搭。官方价格按 token 计费，图片最多折算约 1024 个输入 token。按峰值价格粗略估算，单件衣物识别通常仍在人民币“分”以下，模型费用不是早期主要成本。

建议用途：

- 单件衣物视觉识别；
- 结构化字段提取；
- 文字库存的搭配选择；
- 重复候选解释。

### Gemini

适合用作视觉识别对照组。早期应拿同一批 50—100 张真实衣物照片，同时测试 DeepSeek 与 Gemini，比较字段正确率、响应时间和失败率，再决定默认模型。

### OpenAI

可作为更高质量或故障回退通道，不必在免费版中默认使用。

### Ollama

适合隐私敏感的自托管版本，不适合公众号大众产品的默认方案。普通服务器 CPU 识别可能需要几十秒，用户体验和运维成本未必比云模型更便宜。

## 天气服务

原型阶段可以使用 Open-Meteo 获取天气，无需 API key。正式收费后要注意：其开放免费接口只适合评估和非商业使用；商业产品需要购买商业许可或改用其他合规天气服务。天气结果建议缓存 30—60 分钟，同一城市用户共享缓存，避免重复请求。

物光只需要这些字段：

- 当前温度与体感温度；
- 当日最高、最低温；
- 降水概率与天气代码；
- 风速；
- 用户所在城市或经纬度。

## 分阶段路线

### P0：天气穿搭，不调用 AI

- 用户选择城市和场合；
- 获取天气；
- 用温度、降雨和最近使用次数筛选衣物；
- 展示 2—3 套规则组合；
- 记录“穿了”“不喜欢”。

目标：验证用户是否真的会在早晨打开这个功能。

### P1：AI 单件识别

- 上传单件照片；
- 自动生成名称、分类、颜色、季节和置信度；
- 用户修改后入库；
- 记录每个字段是否被修改。

核心指标：每件物品平均需要修改多少字段，以及从拍照到入库需要多少秒。

### P2：AI 天气穿搭

- 规则先筛候选；
- 模型只选择真实库存 ID；
- 支持通勤、休闲、约会、运动等场合；
- 支持“今天想穿这件”；
- 收集喜欢、不喜欢和实际穿着反馈。

### P3：账户、云同步与收费

- 用户身份和跨设备物品库；
- 图片对象存储；
- AI 调用额度与账单；
- 家庭共享；
- 微信支付或其他支付渠道；
- 数据导出与删除。

## 收费闭环

建议先卖结果，不要一开始就卖“AI”概念。

### 免费版

- 本地物品库；
- 手动录入；
- 基础规则穿搭；
- 少量 AI 识别体验额度。

### 轻会员

- 更多 AI 识别额度；
- 天气与场合穿搭；
- 重复购买提醒；
- 云端同步和完整备份；
- 穿着统计与单次使用成本。

### 定制服务

- 帮用户批量建立数字衣橱；
- 根据职业、场合、偏好和体感温度定制穿搭规则；
- 生成旅行行李清单或一周穿搭；
- 为整理师、造型师提供客户衣橱管理空间。

早期比月订阅更容易验证的收费方式是：

- AI 识别次数包；
- 一次性数字衣橱整理服务；
- 一次性季节穿搭报告；
- 面向整理师或造型师的客户空间年费。

## 下一步实施建议

先准备 50—100 张真实衣物照片作为评测集，人工标注名称、分类、主色和季节。用 DeepSeek Flash 和 Gemini 分别识别，计算：

- 分类准确率；
- 颜色准确率；
- 可直接确认的比例；
- 平均响应时间；
- 单张成本；
- 无法解析 JSON 的比例。

只有当“无需修改或只改一个字段”的比例达到可接受水平，再把识别入口放进正式物光。天气穿搭可以与评测并行开发，因为它主要依赖现有库存和规则，不依赖视觉模型是否成熟。
