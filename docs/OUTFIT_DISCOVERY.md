# 穿搭组合发现算法

本文记录物光如何处理衣物增加后的组合爆炸问题，以及对开源衣橱项目的比较。

## 其他项目如何处理组合爆炸

开源项目大致采用四类方案。它们解决的问题并不完全相同：有的控制计算规模，有的只减少用户看到的数量，有的通过要求用户手动保存穿搭来回避自动生成。

| 路线 | 代表项目 | 核心方法 | 局限 |
|---|---|---|---|
| 确定性剪枝＋批量评分 | Aether Wardrobe | 规则生成候选，按正式度、季节和颜色冲突提前删除；小模型批量评分，只保存高分组合 | 需要较完整的衣物属性和组合数据层 |
| 规则预筛＋AI 选择 | Hangar、Wardrowbe | 先按天气、场合等压缩库存，再让 AI 返回少量库存 ID | 不保证搜索完整，每次推荐通常需要模型调用 |
| 人工保存＋标签检索 | Wardrobe | 用户建立确认过的穿搭，按季节、温度和标签过滤 | 维护成本较高，不能自动发现大量新组合 |
| 逐位置贪心选择 | 一些轻量衣橱项目 | 依次选择当前得分最高的上装、下装、鞋履和外套 | 速度快，但局部最优不一定形成整体最优 |

### Aether Wardrobe：目前最完整的参考实现

Aether Wardrobe 把组合表作为推荐的事实来源：

```text
新增衣物
→ 确定性候选引擎生成结构合法的组合
→ 正式度、季节和明显颜色冲突剪枝
→ 每 12 套交给小模型批量评分
→ 只保存评分不低于 7 的组合
→ 每日根据场合、天气和近期穿着查询
→ 小模型只重排少量候选并解释
```

这种方法把大量计算放在新增衣物时，日常推荐只需查询已经通过筛选的组合。AI 不负责凭空创造组合，也不需要每天重新理解全部库存。

### Hangar 与 Wardrowbe：减少输入，而非完整枚举

这类方案先利用天气、场合、季节或最近穿着缩小衣物集合，再让模型直接给出一至数套建议。用户不会面对大量组合，但系统未必搜索了全部可行组合。它适合“今天直接告诉我穿什么”，不适合完整浏览组合空间。

### Wardrobe：通过人工确认回避爆炸

Wardrobe 主要检索用户已经建立并保存的穿搭。季节标签可以关联日期或温度范围，再结合多标签筛选。这种方式结果可靠，但需要用户提前维护组合，与物光降低录入成本的原则存在张力。物光可以借鉴标签结构，不应要求普通用户手动建立全部组合。

### 物光当前方案与技术边界

物光 V0.2 当前采用：

```text
有界笛卡尔积
→ 最多生成 2,000 个候选
→ 指定单品筛选
→ 按场合历史和穿着次数排序
→ 每次展示 6 套
```

这个方案解决了手机端的计算阻塞和展示过载，也不产生模型费用。单件衣物现在可以多选日常、通勤、健身和聚会。“帮我选”的日常模式使用完整衣橱和原有历史排序；通勤、健身和聚会先排除不符合当前场合的单品，再优先只适用于较少场合的专用单品，通用基础款仍可补全组合。“自己搭”保留全部衣物，不以场合阻止用户混搭。其边界是：超过 2,000 套后，后续组合可能从未进入候选池，候选生成顺序可能造成偏差；天气、季节、正式度和颜色兼容仍未进入硬规则。

组合结构不能把“上装”视为单一互斥槽位。秋冬穿搭经常同时包含秋衣、毛衣和外套，因此物光将上半身拆成：

```text
贴身层（秋衣、打底）
＋ 保暖中层（毛衣、卫衣）
＋ 外层（大衣、夹克）
```

普通上装仍可单独参与组合。旧数据没有层级字段时默认作为普通上装处理，不要求重新上传；用户可以编辑已有上装补充层级。未来天气规则应决定是否需要贴身层和保暖中层，而不是在所有季节强制叠穿。

### 物光下一阶段算法

下一阶段应从“先生成 2,000 套再排序”升级为“边生成、边剪枝、边保留 Top-K”：

```text
生成一个结构合法的组合
→ 温度、降雨、场合和互斥规则硬过滤
→ 计算确定性基础分
→ 用最小堆持续保留得分最高的 50—100 套
→ AI 只复核前 20—50 套并生成解释
→ 最终向用户展示 3—6 套
```

初始评分可以采用：

```text
总分 =
场合适配 30%
+ 温度天气适配 25%
+ 颜色与风格协调 20%
+ 用户历史偏好 15%
+ 低使用率探索奖励 10%
```

权重必须通过真实采用数据调整，不应长期依赖主观设定。用户的“穿了、收藏、不适合、替换一件”是比模型文字评价更重要的反馈。

### 技术决策

物光采用混合路线：

1. 当前免费本地版继续使用有界候选池，保持零模型费用和快速响应；
2. 增加天气、正式度、季节和场合等结构化字段后，引入硬规则剪枝；
3. 使用 Top-K 队列避免候选顺序偏差和完整排序成本；
4. 只有经过规则筛选的少量候选才交给便宜模型评分；
5. 模型只能返回真实库存 ID，服务端验证后才能展示；
6. 长期保存用户穿过、收藏或否定的组合，临时候选无需全部入库。

## 双模式：快速推荐与逐步搭配

市场上的数字衣橱通常同时满足两种任务：赶时间时直接获得少量答案，以及围绕某件衣物主动探索。物光因此保留两种入口：

```text
帮我选：候选池 → 条件筛选 → 排序 → 每次展示 6 套
自己搭：核心单品 → 动态下一槽位 → 逐步补齐 → 完成并记录
```

“自己搭”对应 seed-item recommendation、outfit completion、interactive outfit builder 和 constraint satisfaction 等概念。它采用延迟生成：尚未走到的槽位不生成完整排列，因此可以从交互层面减少组合爆炸。

核心单品不限于上装。用户可以从下装、连衣裙、外套、鞋履、包袋或配饰开始。系统根据当前选择动态决定下一槽位：

```text
场合
→ 任意核心单品
→ 补齐主体（上装＋下装，或者连衣裙）
→ 贴身层、保暖中层与外套
→ 鞋履
→ 包袋
→ 配饰
```

主体结构属于硬约束，不能跳过；保暖层、外套、鞋包和配饰属于可选约束，可以跳过。连衣裙会跳过下装；以鞋履或包袋为核心时，系统会回到主体结构；以外套为核心时，会继续补内搭和下装。

当前版本使用规则驱动的动态槽位。后续可以加入最少剩余值原则（MRV），优先处理候选最少、约束最强的槽位；自动推荐则可以使用束搜索（Beam Search），每一步只保留少量高分半成品，避免展开整棵组合树。

市场思维上，三层穿衣顺序“贴身层→保暖中层→外层”描述的是物理层次；产品的决策顺序应从用户当前最在意的核心单品开始，再补齐主体、温度层和配饰。固定从上装开始无法覆盖连衣裙、鞋履或外套作为穿搭起点的真实场景。
