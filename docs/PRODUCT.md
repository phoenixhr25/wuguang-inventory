# 产品说明

## 问题

用户往往看不清自己已经拥有什么：重复购买、忘记已有物品、长期闲置，也难以理解物品总价值和使用效率。

传统库存工具像 ERP，字段多、维护累。物光的产品假设是：如果入口从照片开始，并让系统逐渐承担识别和整理工作，个人物品库才可能被持续维护。

## 核心闭环

```text
照片或手动添加
→ 确认名称、分类、数量和金额
→ 形成个人物品库
→ 查询、发现相似和记录使用
→ 得到搭配或处置建议
→ 实际使用并反馈
```

## 当前版本的定位

当前版本是用于验证闭环的本地 MVP，不是完整商业产品，也没有接入 AI。它重点验证：

- 用户是否愿意从一件物品开始；
- 哪些字段最影响录入；
- 用户是否会再次查看库存；
- 基础穿搭与使用记录是否能提高已有物品利用率；
- 完整备份是否足以支撑早期试用。

## 产品原则

- AI 负责降低录入成本，用户保留最终确认权；
- 不把估算金额冒充真实购买价格；
- 不把“没有记录”直接判断为“闲置”；
- 推荐只能使用真实库存中的物品；
- 数据必须可导出、可恢复、可删除；
- 先验证行为和价值，再建设复杂账户与商业系统。

## 关键产品判断：组合生成之后，真正的问题是选择

当衣橱中只有 2 件上装和 2 件下装时，基础组合只有 4 种；当上装、下装、鞋履和外套分别增加到 10、8、4、3 件时，完整排列可能达到 960 种。继续增加包袋和配饰后，组合数量会更快膨胀。

因此，“今天怎么穿”不能把所有排列一次展示给用户。产品需要把问题从“系统能生成多少套”转成“用户怎样在几秒内找到此刻适合的一套”。推荐流程应采用：

```text
全部可能组合
→ 场合、天气和季节等硬条件筛选
→ 可选：指定一件今天想穿的单品
→ 排除清洗中、不合适和刚穿过的单品
→ 按适合度、个人偏好和使用效率排序
→ 每次只展示少量候选
→ 收藏 / 穿过 / 不适合 / 换掉其中一件
```

### 通用场合体系

场合是用户最容易理解的第一层入口。固定选项应保持少而稳定，具体活动通过备注表达：

| 一级场合 | 可覆盖的具体情况 |
|---|---|
| 日常 | 买菜、逛街、普通外出 |
| 通勤 | 上班、上学、一般会议 |
| 正式 | 商务活动、面试、重要会议 |
| 社交 | 聚会、约会、聚餐、看展 |
| 运动 | 健身、跑步、球类 |
| 户外 | 徒步、旅行、露营 |
| 居家 | 在家、休息、远程办公 |

场合不应成为新的录入负担。当前阶段由用户在查看或记录穿搭时选择；收藏组合时可以补充多个适用场合；未来再由 AI 推测正式度、风格、季节和适用场合，用户只确认低置信度结果。

### 大量组合的交互原则

- 默认只展示前 6 套，并提供“换一批”；
- 支持“围绕这件搭配”，让用户锁定一件单品；
- 支持替换组合中的某一件，而不是每次重新开始；
- 支持按最适合、最少穿、最近收藏和历史采用情况排序；
- 只长期保存用户收藏、穿过或明确否定的组合，临时候选实时计算；
- 最近穿过的组合可以降低排序，但不禁止用户再次选择；
- AI 只负责给规则筛选后的候选评分和解释，不能凭空创造库存中不存在的物品。

这一设计参考了 Aether Wardrobe 的候选表和分层筛选、Wardrobe 的标签体系、Hangar 的天气与场合推荐，以及 Wardrowbe 的历史、评分和偏好反馈。它们共同说明：组合规模扩大后，稳定的结构化筛选和反馈闭环比一次生成大量搭配更重要。

## 首轮指标

- 至少录入 1、3、10 件物品的人数；
- 从照片到确认一件物品所需时间；
- 每件物品需要填写或修改的字段数；
- 七日内再次打开比例；
- 查看搭配和记录实际穿着的人数；
- 导出备份的人数；
- 用户最希望自动化的步骤。

进入组合发现阶段后，增加以下指标：

- 用户从打开页面到记录一套穿搭所需时间；
- 选择场合后实际采用推荐的比例；
- “换一批”和“换掉其中一件”的使用次数；
- 收藏后被真正穿着的组合比例；
- 不同场合下重复采用与探索新组合的比例。
