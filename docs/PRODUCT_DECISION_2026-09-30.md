# 产品决策记录：从物品盘点到个人物品档案

中文 · [English](PRODUCT_DECISION_2026-09-30_EN.md)

日期：2026-09-30  
状态：待验证

## 触发反馈

公众号发布后收到一条代表性留言：

> 这也是我一直想拥有的 app，相当于给每一个物品归纳归档，我对我所拥有的物品都有一种情感。

这条反馈提示了物光的第二层价值。用户需要的不只是库存数量、金额和防止重复购买，也可能希望保存物品的来历、记忆和情感。

单条反馈还不足以证明普遍需求，因此本记录把它视为一个需要低成本验证的产品假设，而不是立即全面转向的结论。

## 定位判断

物光当前是通过浏览器使用的 Web MVP，不是需要下载安装的原生 App。长期产品可以同时保留两层价值：

| 层次 | 用户问题 | 主要能力 |
|---|---|---|
| 实用层 | 我有什么、在哪里、是否重复、是否仍在使用 | 盘点、分类、金额、搜索、使用与维护记录 |
| 情感层 | 它从哪里来、为什么留下、对我意味着什么 | “关于它”、时间、故事、照片与分享卡 |

当前定位可表述为：

> 物光帮助人看见自己拥有什么，也帮助人记住为什么愿意留下它。

这不是放弃“减少浪费、提高使用率”的原始方向，而是在其上增加个人物品档案能力。

## 产品本体与传播渠道

短期内继续把网站作为产品本体，不把用户数据依附在微信或小红书内部。

| 载体 | 角色 | 当前判断 |
|---|---|---|
| Web / 未来的 PWA | 物品数据、照片、故事和操作闭环 | 继续作为产品本体 |
| 微信公众号 | 已有用户入口、教育与反馈 | 继续作为主要触达渠道 |
| 小红书 | 物品故事、空间、穿搭内容传播和需求验证 | 作为内容渠道，不作为数据底座 |
| 微信小程序 | 微信内拍照、登录、分享和同步 | 用户留存与微信内使用得到验证后再做 |
| 原生 App | 相机、通知、端侧识别和订阅 | 高频需求和收费闭环出现后再评估 |

推荐路径：

```text
公众号 / 小红书 / 朋友分享
            ↓
         物光 Web
            ↓
   账号与同步需求得到验证
            ↓
      PWA 或微信小程序
            ↓
  必要时再建设原生 App
```

## 近期实验一：“关于它”

为所有物品增加一个完全可选的自由文本字段“关于它”，用于记录来历、赠送者、使用经历或保留原因。

第一版不拆出大量必填字段，避免重新走向 ERP 式录入。待用户自然写出内容后，再判断是否需要获得日期、获得方式、来自谁、纪念物等结构化字段。

需要验证：

- 用户是否愿意填写；
- 哪类物品最常填写；
- 用户写的是功能备注还是情感故事；
- 填写后是否更愿意回看、继续记录或分享。

## 近期实验二：隐私可控的物品故事卡

早期分享采用本地生成的图片卡，而不是公开物品网页。用户主动选择单件物品并决定展示内容，然后保存 PNG 分享到朋友圈、小红书或聊天。

默认内容：物品照片、名称、“关于它”和物光标识。

可选内容：获得或拥有时间、分类，以及与品类匹配的使用或维护信息。

默认隐藏：金额、精确收纳位置、序列号、发票、设备标识、其他物品和完整物品库。

分享主要承担获客和表达价值。真正促进留存的机制仍然是回看故事、维护到期、保修到期、借出归还和阶段性整理。

## 不同品类需要不同闭环

不能把衣物的“今天穿了”机械复制给所有物品。物光需要按品类定义有意义的事件。

| 大品类 | 核心闭环 | 适合记录的事件 |
|---|---|---|
| 衣物 | 搭配—穿着—统计 | 穿过、组合、场合 |
| 家具 | 空间—维护—变化 | 搬动、清洁、维修、翻新、重新布置 |
| 数码 | 使用—维护—生命周期 | 启用、停用、维修、充电、借出、归还、淘汰 |
| 全部物品 | 归档—故事—分享 | 关于它、获得时间、照片和故事卡 |

### 家具

沙发、桌子、床和冰箱等物品可能每天都在使用，要求每日打卡会增加负担而不产生有效数据。家具更适合记录：

- 当前房间或空间；
- 常用、偶尔使用、收纳、待维修、准备处理等状态；
- 最近清洁、维修、搬动或翻新；
- 下次维护时间；
- 拥有时长和物品故事；
- “阅读角”“工作区”等空间组合。

家具分享可以围绕空间和变化，例如旧家具翻新、阅读角形成过程、租房中值得留下的物品。

### 数码

手机和电脑等高频设备适合记录状态、使用年限、维修、保修和配件，而不是每天点击“用过”。相机、游戏机、投影仪等低频设备可以保留具体使用事件。

数码应支持：

- 主力、备用、偶尔使用、闲置、维修中、已淘汰等状态；
- 最近确认仍在使用；
- 保修和维修记录；
- 设备与配件组成的装备；
- 借出与归还；
- 使用年限和处置判断。

数码故事卡可以表达长期使用感受、通勤装备或旅行摄影组合，但必须默认隐藏序列号、发票、位置和网络信息。

## 使用度量模型

统一的 `useCount` 无法解释所有品类。后续模型至少拆成：

1. **事件频率**：衣物、相机、游戏机、露营用品等在一定时间内发生多少次真实使用；
2. **状态确认**：手机、电脑、冰箱和家具等当前是否仍在使用；
3. **维护频率**：清洁、充电、维修或保养距离上次发生了多久。

跨品类公共字段可以逐步演进为：

```text
story / 关于它
status / 当前状态
lastMeaningfulUseAt / 最近一次有意义的使用
events / 使用、维护、搬动、维修、借出、归还等事件
```

统计界面必须区分事件类型，不能把一次维修和一次日常使用混为同一个“使用次数”。

## 开源项目参考

以下项目用于学习公开工作流，不代表物光已经复制或引入其代码。若未来复用代码，必须单独核对许可证并保留相应声明。

- [HomeBox](https://github.com/sysadminsmedia/homebox)：家庭物品、位置、自定义字段、保修和维护；
- [HomeInventory](https://github.com/asdteke/HomeInventory)：房间、借用、维护、活动历史、二维码和隐私分级；
- [Grocy](https://github.com/grocy/grocy)：周期任务、执行记录、到期时间、电池和家庭事务；
- [Shelf](https://github.com/Shelf-nu/shelf.nu)：设备借还、位置、套装、提醒和审计历史；
- [DumbAssets](https://github.com/DumbWareio/DumbAssets)：设备、部件、保修和维修提醒；
- [itemLens](https://github.com/romland/itemLens)：低录入成本与“它在哪里、有什么用、为什么购买”；
- [toop-closet](https://github.com/akleventis/toop-closet)：单品与组合分享链接及公开读取边界。

## 实施顺序

### 第一阶段：低成本验证

- 所有品类增加可选“关于它”；
- “关于它”进入编辑、展示、搜索和完整备份；
- 所有品类可生成单件物品故事卡；
- 分享时默认隐藏敏感字段；
- 记录故事字段填写率、故事卡生成率和分享意愿。

### 第二阶段：品类事件

- 家具增加清洁、维修、搬动和重新布置；
- 数码增加设备状态、维修、借出和归还；
- 按品类显示不同统计；
- 建立物品时间线。

### 第三阶段：提醒与同步

- 维护、保修和借出到期提醒；
- 账号与跨设备同步；
- 家庭空间和权限；
- 根据真实留存和渠道数据决定 PWA、微信小程序或原生 App。

## 需要持续验证的信号

- 是否出现更多关于物品情感、来历和纪念意义的反馈；
- “关于它”的填写率和平均内容长度；
- 哪些品类最容易形成故事；
- 故事卡生成后是否真的被保存或分享；
- 分享是否带来新用户完成首次入库；
- 维护、保修、借出等提醒是否带来回访；
- 用户是否愿意为了云同步、家庭共享或 AI 整理付费。
